AsteriskIA Agentes

Plataforma de monitoramento inteligente e automação de infraestrutura com suporte a múltiplos provedores de IA. Monitore servidores SSH, URLs, logs e bancos de dados com alertas em tempo real e capacidade de auto-remediação.

Visão Geral

O AsteriskIA Agentes é uma plataforma de monitoramento autônomo integrada ao ecossistema AsteriskIA Telecom. Cada Agente é uma entidade configurável que executa verificações periódicas em servidores, URLs ou bancos de dados, registra os resultados, notifica a equipe em caso de falha e pode até tentar corrigir o problema automaticamente.

🔍 Monitoramento

4 tipos de executores: SSH Test, Web Monitor, Log Monitor e Database. Cada um com múltiplas verificações configuráveis por agente.

🤖 Inteligência Artificial

Fallback para IA quando uma verificação falha sem fix_hint. Suporte a Google Gemini, Anthropic Claude, OpenAI e modelos locais.

🔔 Alertas Multi-canal

Telegram, e-mail SMTP, webhook genérico e notificações em tempo real via WebSocket no painel.

🔧 Auto-Fix

Execute comandos de correção automaticamente via SSH quando uma verificação falha, sem intervenção humana.

🔗 Encadeamento

Configure um agente para disparar outro automaticamente em caso de falha — criando pipelines de diagnóstico.

📊 Memória e RAG

Cada agente aprende com execuções passadas. A memória coletiva é consultada via pg_trgm antes de acionar a IA.

ℹ️

O frontend usa const API = '/agents'. Todas as chamadas de API ficam em /agents/api/* que o Caddy roteia para o backend na porta 8000. O login usa o backend Spring Boot do Telecom via /api/v1/auth/login.

Fluxo de autenticação

1

Login via Spring Boot

O frontend envia POST /api/v1/auth/login com usuário e senha para o backend Telecom (Spring Boot). Em caso de 2FA ativo, é necessário completar o TOTP antes de receber o token final.

2

JWT armazenado

O token JWT é salvo no localStorage com a chave asteriskia_token. Tem validade de 8 horas. Tokens com totp_pending: true são rejeitados pelo backend dos agentes.

3

Injeção automática

Todas as chamadas à API dos agentes incluem automaticamente o header Authorization: Bearer <token>. Em caso de 401, o token é limpo e a página recarrega.

Tipo: SSH Test

Conecta ao servidor via SSH e executa uma sequência de comandos shell, avaliando a saída de cada um contra critérios configuráveis.

ℹ️

Pré-requisito: O servidor precisa estar cadastrado na página Servidores com credenciais válidas. O agente do tipo SSH requer ao menos um servidor associado para executar com sucesso.

Campos específicos

CampoTipoDescrição
Servidores alvo checkboxes obrigatório Selecione um ou mais servidores cadastrados. O agente executará todas as verificações em cada servidor selecionado.

Verificações (checks)

Cada verificação representa um comando a ser executado no servidor. Adicione quantas quiser com o botão + Adicionar.

CampoTipoDescrição
Nome texto Nome descritivo da verificação. Aparece nos logs e alertas. Ex: "nginx rodando", "disco livre".
Comando texto Comando shell executado no servidor remoto via SSH. Ex: systemctl is-active nginx, df / | awk 'NR==2{print $5}'.
Saída esperada texto Valor exato que a saída do comando deve retornar (comparação ==). Ex: active. Pode ser substituído pelos campos expect_* avançados via JSON.
Dica de correção texto Texto informativo mostrado no alerta quando a verificação falha. Ex: sudo systemctl restart nginx. Se preenchido, substitui a consulta à IA.
fix_cmd JSON Comando executável automaticamente via SSH quando falha + "auto_fix": true. Ver seção Auto-Fix.

Critérios de avaliação avançados (via JSON)

O campo Rules aceita JSON completo para configuração avançada. Os critérios disponíveis por check são:

CritérioComportamentoExemplo
expectSaída exata (igualdade estrita)"expect": "active"
expect_containsSaída deve conter a string"expect_contains": ":80"
expect_ltValor numérico menor que"expect_lt": "80%"
expect_exitExit code específico"expect_exit": 0
expect_regexExpressão regular"expect_regex": "^[0-9]+$"

Exemplo completo de Rules (SSH Test)

📋 Exemplo — Monitor de Servidor Asterisk
{
  "checks": [
    {
      "name":     "asterisk rodando",
      "cmd":      "systemctl is-active asterisk",
      "expect":   "active",
      "fix_hint": "sudo systemctl restart asterisk",
      "fix_cmd":  "sudo systemctl restart asterisk",
      "auto_fix": true
    },
    {
      "name":       "disco livre (raiz)",
      "cmd":        "df / | awk 'NR==2{print $5}'",
      "expect_lt":  "80%",
      "fix_hint":  "Limpar logs: journalctl --vacuum-time=3d"
    },
    {
      "name":            "porta SIP 5060 aberta",
      "cmd":             "ss -ulnp | grep :5060",
      "expect_contains": ":5060",
      "fix_hint":        "Verificar firewall: ufw allow 5060/udp"
    },
    {
      "name":         "script de health",
      "cmd":          "/opt/asterisk/health_check.sh",
      "expect_exit":  0
    }
  ],
  "timeout_per_check":     30,
  "stop_on_first_failure": false,
  "use_ai_on_failure":     true
}

timeout_per_check30Segundos máximos por comando SSH antes de timeout.
stop_on_first_failurefalseSe true, interrompe os checks restantes assim que um falhar.

Tipo: Web Monitor

Realiza requisições HTTP/HTTPS para URLs configuradas e valida o status, conteúdo ou estrutura JSON da resposta.

🌐 Exemplo — Monitor de APIs e Portais
{
  "checks": [
    {
      "url":           "https://app.voiphash.com.br",
      "expect_status": 200,
      "expect_contains": "AsteriskIA",
      "timeout":        10
    },
    {
      "url":               "https://app.voiphash.com.br/api/health",
      "expect_status":   200,
      "expect_json_key": "status",
      "expect_json_value": "ok"
    },
    {
      "url":           "https://api.parceiro.com.br/v2/ping",
      "expect_status": 200,
      "timeout":        5
    }
  ],
  "alert_on_failure":  true,
  "use_ai_on_failure": false
}
Critério por checkDescrição
urlURL completa a verificar. Deve incluir o protocolo (https://).
expect_statusCódigo HTTP esperado. Padrão 200. Ex: 301, 204.
expect_containsString que deve estar presente no corpo da resposta.
expect_json_keyChave de JSON esperada no body (usado com expect_json_value).
expect_json_valueValor esperado para a chave JSON. Ex: "ok", "true", "1".
timeoutTimeout em segundos para esta URL. Padrão: 15.

Tipo: Log Monitor

Conecta ao servidor via SSH, lê as últimas N linhas de arquivos de log e verifica se padrões de texto esperados (ou inesperados) estão presentes.

📄 Exemplo — Monitor de Logs Asterisk e Nginx
{
  "log_checks": [
    {
      "name":          "erros críticos nginx",
      "file":          "/var/log/nginx/error.log",
      "pattern":       "ERROR|CRIT|emerg",
      "alert_if_found": true,
      "lines":          100,
      "fix_hint":       "nginx -t && systemctl restart nginx"
    },
    {
      "name":             "asterisk warnings acumulados",
      "file":             "/var/log/asterisk/messages",
      "pattern":          "WARNING|ERROR",
      "alert_if_found":   true,
      "lines":             200,
      "min_occurrences":  5
    },
    {
      "name":          "heartbeat systemd presente",
      "file":          "/var/log/syslog",
      "pattern":       "Started Daily",
      "alert_if_found": false,
      // alert_if_found: false = alerta se NÃO encontrar
      "lines":          50
    }
  ],
  "timeout_per_check": 30,
  "use_ai_on_failure": true
}
CampoDescrição
fileCaminho absoluto do arquivo de log no servidor remoto.
patternRegex ou string buscada nas últimas lines linhas do arquivo. Suporta pipe | para múltiplas alternativas.
alert_if_foundtrue: falha se o padrão for encontrado (ex: erros). false: falha se o padrão não for encontrado (ex: heartbeat).
linesQuantas linhas a partir do final do arquivo serão analisadas. Padrão: 100.
min_occurrencesMínimo de ocorrências para considerar como falha. Útil para ignorar erros esporádicos.

Tipo: Database

Executa queries SQL diretamente em bancos de dados PostgreSQL e avalia os resultados contra thresholds configuráveis. Ideal para monitorar métricas de negócio.

⚠️

Atenção: O DSN (string de conexão) contém senha. Recomendamos usar Secrets para armazenar o DSN completo e referenciá-lo como {{DB_DSN}} no campo dsn.

🗄️ Exemplo — Monitor de Banco do Telecom
{
  "checks": [
    {
      "name":        "chamadas com falha na última hora",
      "dsn":         "postgresql://user:pass@host:5432/asteriskia",
      "query":       "SELECT COUNT(*) FROM call_records WHERE status='failed' AND call_date > NOW()-INTERVAL '1h'",
      "expect_lt":   10,
      "fix_hint":    "Verificar trunk SIP — possível problema de rota"
    },
    {
      "name":        "conexões ativas no banco",
      "dsn":         "postgresql://user:pass@host:5432/asteriskia",
      "query":       "SELECT COUNT(*) FROM pg_stat_activity WHERE state='active'",
      "expect_lt":   50
    },
    {
      "name":         "status do sistema",
      "dsn":          "postgresql://user:pass@host:5432/asteriskia",
      "query":        "SELECT value FROM system_config WHERE key='status'",
      "expect_eq":    "active"
    }
  ],
  "timeout":          30,
  "use_ai_on_failure": false
}
CritérioComparaçãoExemplo
expect_eqResultado == valor"expect_eq": "active"
expect_ltResultado < valor numérico"expect_lt": 10
expect_gtResultado > valor numérico"expect_gt": 0
expect_zeroResultado == 0"expect_zero": true

Agendamento

Define a frequência com que o agente executa automaticamente. O próximo horário é calculado e exibido na coluna "Ultima / Proxima" da tabela.

TipoCampo "Valor"ExemplosComportamento
Intervalo 5m, 1h, 30s, 2d 5m, 1h, 6h, 24h Aguarda o intervalo após cada execução antes de rodar novamente.
Cron Expressão cron (5 campos) 0 2 * * *, */15 * * * *, 0 8 * * 1-5 Executa nos horários definidos pela expressão. Usa croniter para calcular o próximo gatilho.
Sempre ativo — — Reexecuta 10 segundos após cada término. Ideal para monitoramento contínuo.
Uma vez — — Executa uma única vez quando o agente é salvo ou reiniciado.
✅

Unidades de intervalo: s = segundos · m = minutos · h = horas · d = dias. Ex: 30s, 5m, 2h, 1d.

Exemplos de expressões cron

0 * * * *      # A cada hora (no minuto zero)
*/5 * * * *    # A cada 5 minutos
0 2 * * *      # Todo dia às 02:00
0 8 * * 1-5   # Dias úteis às 08:00
0 0 1 * *      # Primeiro dia de cada mês à meia-noite

Auto-Fix

Quando uma verificação SSH falha, o sistema pode executar automaticamente um comando de correção no servidor, sem intervenção humana.

⚠️

Use com cuidado. O auto-fix executa como o usuário SSH configurado no servidor. Certifique-se de que o usuário tem as permissões necessárias e de que o comando é seguro para execução automática.

Como configurar

Adicione fix_cmd e "auto_fix": true ao check no JSON de Rules:

{
  "name":      "nginx rodando",
  "cmd":       "systemctl is-active nginx",
  "expect":    "active",
  "fix_hint":  "Reiniciar nginx",
  "fix_cmd":   "sudo systemctl restart nginx",
  "auto_fix":  true
}

Fluxo de execução

Check falha
→
auto_fix = true?
→
Executa fix_cmd via SSH
→
Log do resultado

O resultado do fix_cmd é registrado nos logs da execução com o marcador 🔧 Auto-fix. Se o comando falhar, o log exibe 🔧 Auto-fix falhou.

Encadeamento de Agentes

Configure um agente para disparar automaticamente outro agente quando falhar. Útil para criar pipelines de diagnóstico: um agente detecta o problema, outro investiga a causa.

ℹ️

O encadeamento é limitado a 3 níveis de profundidade para evitar loops. Agente A → B → C → D seria interrompido em D.

Exemplo de uso

Agente "Web Monitor API" detecta que a URL da API retornou 503.

→ Dispara o Agente "SSH Diagnóstico Backend" que conecta ao servidor e verifica se o processo FastAPI está rodando, uso de memória e erros recentes nos logs.

Configure o campo on_failure_trigger_agent_id via API ou diretamente no banco. Uma interface visual para esse campo no formulário está no roadmap.

Consulta automática pela IA

Como usar Secrets nos checks

Após cadastrar um secret com a chave DB_PASSWORD, referencie-o no comando do check com a sintaxe {{DB_PASSWORD}}. O valor é substituído em tempo de execução antes do comando ser enviado ao servidor.

Exemplo de uso em SSH Test
{
  "name": "testar conexão banco",
  "cmd":  "PGPASSWORD={{DB_PASSWORD}} psql -U dbuser -h localhost -c 'SELECT 1'",
  "expect_exit": 0
}
🔒

Segurança: Valores de secrets são armazenados na tabela agent_secrets e nunca retornados pela API de listagem — apenas as chaves aparecem na interface. Acesso restrito ao agente dono do secret.

Health Check

Endpoint público para monitoramento externo do sistema. Não requer autenticação JWT.

GET /api/system/health
Resposta — sistema saudável
{
  "status":   "ok",
  "database": "ok",
  "agents":   3,
  "running":  0,
  "version":  "2.0.0"
}
CampoValoresSignificado
statusok / degradeddegraded quando o banco não responde.
databaseok / errorEstado da conexão com o PostgreSQL.
agentsnúmeroTotal de agentes cadastrados.
runningnúmeroAgentes com status running no momento.

Configure um uptime monitor externo (UptimeRobot, Betteruptime etc.) apontando para https://app.voiphash.com.br/agents/api/system/health com verificação de "status":"ok" no body.

Retenção de Dados

Configura por quanto tempo execuções, logs e alertas são mantidos no banco. A limpeza roda automaticamente em background com probabilidade de 1% em cada execução de agente.

GET /api/system/retention Lê configuração atual
PUT /api/system/retention Atualiza configuração
POST /api/system/retention/run Força limpeza imediata
PUT /api/system/retention — body
{
  "executions_days": 90,   // padrão: 90 dias
  "logs_days":       30,   // padrão: 30 dias
  "alerts_days":     180  // padrão: 180 dias
}
⚠️

Execuções com status running nunca são deletadas automaticamente, mesmo que ultrapassem o limite de dias, para evitar perda de dados em andamento.
