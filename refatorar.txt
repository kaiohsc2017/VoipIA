Fase 1 — Prompt de auditoria (gera o roadmap, zero código)
Aja como engenheiro de software sênior fazendo uma auditoria arquitetural
do sistema AsteriskIA. NESTA FASE VOCÊ NÃO ESCREVE CÓDIGO — o objetivo é
produzir um roadmap de refatoração priorizado.

## Contexto do sistema
Plataforma VoIP + IA de contact center. 8 containers Docker:
- Asterisk 21 LTS
- Backend: Spring Boot 3.3 / Java 21
- Frontend: React 18 + TypeScript (build via npm)
- Agents platform: FastAPI / Python 3.12
- Agente IA: Python asyncio
- PostgreSQL 16
- Caddy (proxy, rotas /agents/*)
- Fail2ban
Repo: github.com/kaiohsc2017/AsteriskIA · VPS: /opt/AsteriskIA
Deploy: git pull no main. Commits com prefixo telecom:/agents:.

## O que analisar (por módulo, separadamente)
Para CADA base de código (backend Java, frontend React, agents FastAPI,
agente asyncio):
1. Code smells e violações de SOLID concretas, com arquivo/linha.
2. Acoplamento indevido e fronteiras de módulo mal definidas.
3. Duplicação (dentro do módulo e entre módulos).
4. Pontos de risco: tratamento de erro, concorrência (asyncio/@Scheduled),
   validação de entrada, gestão de segredos.
5. Dívida técnica que já causou bugs (ex: tipos públicos declarados
   dentro de controllers, parâmetros JPQL não tipados).

## Formato da saída
Uma TABELA de achados com: módulo | problema | severidade (alta/média/baixa)
| esforço estimado | risco de regressão | prioridade sugerida.
Depois, um roadmap ordenado: o que refatorar primeiro e por quê, agrupando
mudanças que fazem sentido juntas.

## Restrições
- Não proponha reescrever tudo. Priorize impacto/risco.
- Não sugira dependências novas sem justificar o custo.
- Sinalize claramente o que é "melhoria de estilo" vs "risco real".

## Processo obrigatório
1. DIAGNÓSTICO primeiro: confirme os problemas do roadmap neste código e
   liste os que encontrar a mais. Sem escrever código ainda.
2. Proponha a refatoração como DIFF, não reescrevendo arquivos inteiros.
3. Explique o trade-off de cada decisão relevante.
4. Liste os edge cases que a versão atual quebra ou ignora.
5. Indique quais testes cobririam o comportamento preservado.
6. Se houver tipos públicos dentro de controllers, extraia para arquivos
   próprios (padrão recorrente de falha de build neste projeto).
